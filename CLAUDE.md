# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

InkyPi-Layout is a third-party plugin for [InkyPi](https://github.com/jtn0123/InkyPi), an e-ink display app for Raspberry Pi. It's a meta-plugin: it composes other already-installed InkyPi plugins into named rectangular regions on one screen (e.g. weather + blood glucose + calendar + a menu strip together), rather than fetching any data of its own.

This repo is *not* a standalone application — it contains only the plugin, meant to be installed into an existing InkyPi instance. The entire repo's content is the single `layout/` folder (plus README/LICENSE/docs/tests); nothing here runs on its own. **Requires [jtn0123/InkyPi](https://github.com/jtn0123/InkyPi). It does not work on upstream [fatihak/InkyPi](https://github.com/fatihak/InkyPi)** — this is a hard requirement, not a difference in install steps. Composing other plugins' output means calling into the host's internal plugin registry (`plugins.plugin_registry.get_plugin_instance`) to instantiate and invoke them, and that capability exists only in the fork. There is no compatibility path, so don't add upstream-compatibility shims here the way `BloodSugar` does for its one fork-only import — for Layout the fork dependency is the whole mechanism. README's Compatibility section states the same thing for end users; keep the two in step.

## Installation (end-user)

```bash
inkypi plugin install layout https://github.com/cartagena/InkyPi-Layout
```

This is InkyPi's plugin CLI: it does a `git sparse-checkout` of the folder named exactly after the plugin id and copies its contents into `<inkypi>/src/plugins/layout`. **The top-level `layout/` folder name must exactly match `plugin-info.json`'s `"id"` field** — a hard requirement of the install mechanism, not just a convention.

Layout has no external API/credentials of its own — whatever a region's assigned child plugin needs (API keys, settings), configure exactly as that plugin's own docs describe.

## Verifying changes

Two suites, split by what they require. **The old "copy the test file into an InkyPi checkout" workflow is gone** — both suites now run from this repo.

```bash
pip install -r requirements-dev.txt
pytest tests/unit                    # anywhere: no InkyPi, no network, no browser
INKYPI_PATH=../InkyPi pytest         # everything, against a real InkyPi checkout
```

`tests/conftest.py` is what makes that work. It registers stand-ins for the four host modules `layout.py` imports (`BasePlugin`, the settings-schema DSL, `plugin_registry`, `resolve_path`) **only when a real InkyPi isn't importable**; when `INKYPI_PATH` is set it puts `<inkypi>/src` on `sys.path` and stubs nothing, so the identical unit tests run against real host code. CI runs the unit suite both ways deliberately — that's the mechanism that stops these stubs from drifting away from InkyPi's actual behaviour.

Two consequences worth keeping in mind when editing these files:

- **The stubs must stay minimal.** They cover exactly what `layout.py` imports. Adding a new host import to the plugin means adding its stub — don't grow `tests/conftest.py` into a general-purpose fake InkyPi, since a rich fake is precisely what starts passing when the real host has changed.
- **If `INKYPI_PATH` is set but the host still won't import, the conftest raises rather than falling back to stubs.** Silently stubbing there would let CI's integration job report green while having quietly run the unit suite twice.

`tests/integration/` needs `layout/` symlinked into the checkout (`ln -s <this-repo>/layout <inkypi-checkout>/src/plugins/layout`) because `BasePlugin` resolves `render_dir`/`get_plugin_dir` relative to `src/plugins/<id>`; the conftest's skip message says so if it's missing. Its tests are the ones that can only be verified against real host code: loading through the real registry, `plugin-info.json` agreeing with the registered class, the region editor surviving the real `settings_schema.html` widget macros, `_list_available_plugins` scanning a real `plugins/` dir, and real child plugins (`clock`, `year_progress` — chosen for needing no API key or network) rendering through headless Chromium into one composite.

The unit suite (`tests/unit/test_layout.py`) **always fakes child plugins** (`FakeColorPlugin`, patched in via `plugins.layout.layout.get_plugin_instance`) — never call real Dexcom/Nutrislice/Weather/Calendar APIs from this file. It covers: pixel-accurate region placement, region borders, out-of-bounds/negative-offset/self-reference/unknown-plugin validation errors, per-region `refresh_minutes` caching (cache hit skips the child call, expired cache re-invokes it, no-`refresh_minutes` always re-renders), stale-cache pruning, stale-cache fallback on a child render failure, placeholder rendering when a child fails with no cache yet, auto-resize when a child returns the wrong image size, and the settings-template's `available_plugins`/`presets_json` output.

**Any test that calls `generate_image` more than once must route `settings` through `_as_subprocess_would()`** (a deep copy), never pass the same dict twice. Production hands the plugin a fresh pickled copy per refresh; a shared dict gives Layout a cross-refresh persistence channel it doesn't actually have, and that is precisely what hid the broken `refresh_minutes` cache described under Architecture below.

`py_compile` on `layout/layout.py` catches syntax errors without needing InkyPi at all. Don't start InkyPi's Flask dev server to test this plugin's *Python* logic — the direct `generate_image()` calls the test suite (or a manual script following the same pattern) uses are faster and don't need a running server or child plugins' live APIs.

**Exception: `layout/settings.html`'s browser/JS behavior (the drag/resize canvas, and any future region-editor JS) has no pytest coverage and no JS test runner exists in this repo** — `test_layout.py` only exercises the Python side (`_parse_regions`/`_validate_region`/`generate_image`), which is unaffected by changes confined to this file. Verify that behavior manually: symlink `layout/` into a local InkyPi checkout as above, run `.venv/bin/python src/inkypi.py --dev --web-only` from that checkout, and exercise the settings page in a real browser (or drive it with Playwright, already a dependency of InkyPi's own checkout, for scripted verification).

## Architecture

- **`layout/layout.py`** — the `Layout(BasePlugin)` class InkyPi loads. `generate_image(settings, device_config)` parses `regionsJson`, validates every region against the real configured canvas resolution (the sole authority on bounds), then for each region calls the target plugin's own unmodified `generate_image()` — scoped to the region's exact pixel size via `_RegionDeviceConfig` — and pastes the result onto the full canvas at `(x, y)` with a 1px black border. `validate_settings` runs only the resolution-*independent* checks (`_validate_region_shape`: positive w/h, non-negative x/y, non-negative `refresh_minutes`), because it receives no `device_config` and so cannot know the canvas size.
- **`_RegionDeviceConfig`** — a `device_config` proxy each child plugin receives instead of the real one. Reports the region's `(w, h)` as `get_resolution()` so the child's own internal layout logic (font sizes, wrapping) adapts to the region size instead of rendering full-screen and getting cropped, and pins `orientation` to `"horizontal"` so `BasePlugin.get_oriented_dimensions()` doesn't re-swap w/h based on the *device's* orientation setting. Everything else (timezone, `load_env_key`, `plugin_image_dir`) delegates straight through to the real `device_config` via `__getattr__`.
- **Per-region caching** (`_render_region`/`_store_cache`/`_load_cached_image`/`_cache_timestamp`) — keyed by a hash of `(plugin_id, x, y, w, h, settings)` plus region index, persisted as PNG files under `<plugin_image_dir>/layout/`. A region with `refresh_minutes` set skips re-invoking its child plugin (and thus its upstream API) if the cached render is still within that window; a region without `refresh_minutes` always re-renders. **This only throttles child-plugin invocations — it does not reduce the physical e-paper panel's own refresh cadence**, which is controlled by this Layout instance's playlist refresh interval (the operator's responsibility to set to the fastest region's needs).
  - **The cache lives entirely on disk — never in the `settings` dict.** The file's own mtime *is* the "cached at" timestamp (`_cache_timestamp`); there is no cache index. This is load-bearing, not stylistic: InkyPi runs `generate_image()` in a subprocess (`INKYPI_PLUGIN_ISOLATION` defaults to `"process"` — see `refresh_task/executor.py` and `refresh_task/worker.py`), so `settings` arrives as a **pickled copy** and anything written back into it is discarded when the child exits. An earlier version kept the index in `settings["_layout_cache"]`, which meant every refresh started from an empty index: `refresh_minutes` never actually skipped a child call, and the stale-image fallback never found an image to fall back to. Neither feature worked in production, and the test suite missed it by passing one long-lived `settings` dict across several `generate_image()` calls — `test_layout.py`'s `_as_subprocess_would()` helper now deep-copies per call to model the real boundary. Any future per-refresh state must go to disk for the same reason.
  - **`_prune_cache_dir`** sweeps cache files older than `CACHE_MAX_AGE_DAYS` (14) at the top of each `generate_image()`. Every edit to a region's geometry or settings changes its cache key and orphans the previous file, so without this the directory grows for the life of the install. Pruning is by *age*, deliberately not by "not referenced by the regions I just rendered" — multiple Layout playlist instances share this one directory, and a set-difference sweep would have each instance delete the others' still-live entries on every refresh.
- **Graceful degradation** — if a child's `generate_image()` raises, Layout logs the error and falls back to that region's last successfully cached image rather than failing the whole composite; if there's no cache yet, it renders a plain "`<plugin_id>` unavailable" placeholder box instead. A missing/unregistered `plugin_id`, by contrast, is treated as a configuration mistake and fails loudly (`RuntimeError`) rather than going through this fallback path — see the comment above the `device_config.get_plugin(...)` check in `generate_image`.
- **`HOME_PRESET`** (in `layout.py`) — a concrete 4-region "Home screen" preset (`weather` full-width top strip, `blood_sugar` + `calendar` side by side, `nutrislice` full-width bottom strip) that doubles as this plugin's real-world reference composition. `PRESETS` is a dict keyed by preset id for the settings UI's preset picker. **Preset regions are stored as fractions of the canvas (0.0–1.0), not pixels** — `settings.html`'s `scalePreset()` multiplies them by the real `CANVAS_W`/`CANVAS_H` when the preset button is clicked. Pixel-valued presets only ever landed correctly on the one panel size they were drawn for, and on a smaller panel produced regions that failed validation outright. `scalePreset` converts each *edge* and derives `w`/`h` from the difference between converted edges, rather than rounding `x` and `w` independently, so adjacent regions stay flush and the last one can't round past the canvas edge. `test_layout.py::test_presets_are_expressed_as_canvas_fractions` pins the fraction invariant.
- **`layout/settings.html`** — JS-driven region editor (add/remove regions, per-region plugin dropdown populated from `available_plugins`, x/y/w/h number inputs, and preset buttons that bulk-fill from `presets_json`), plus a visual drag/resize canvas (`renderCanvas`/`updateCanvasBox`/`startDrag`) — one labeled, colored box per region, sized responsively via CSS percentage positioning so it works at any rendered width. The canvas's pixel coordinate space (`CANVAS_W`/`CANVAS_H`, in Jinja: `canvas_w`/`canvas_h`) is **not** hardcoded — it's computed at template-render time from `resolution`/`config.orientation`, which `plugin_page()` already passes into `plugin.html`'s Jinja context and which this file inherits for free via `{% include %}`'s default context-sharing (no InkyPi change needed; see the `{# ... #}` comment and `{% set %}` block at the top of this file). Falls back to the documented 800×480 default only when those variables aren't in scope at all (e.g. a template unit test rendering this partial directly, outside `plugin.html`) — this repo has no such test today (`test_layout.py` only checks `generate_settings_template()`'s returned dict, never renders this template), so that fallback path is currently unexercised by any test. Verified manually across resolution/orientation combinations (e.g. `resolution:[1600,1200]` + `orientation:vertical` correctly yields a 1200×1600 canvas, matching `get_oriented_dimensions()`'s own swap) — see "Verifying changes" below. Dragging a box (Pointer Events, clamped in-bounds) updates `x`/`y`; dragging its bottom-right handle updates `w`/`h`; both stay bidirectionally in sync with the existing number inputs and feed the same `sync()`/`validate()` path, so bounds-checking is unchanged. Each box also shows its height/width as a percentage of the canvas (`percentLabelText`), updated live during drag/resize. `rectsOverlap`/`blockingOverlap` block a drag/resize from *introducing* new overlap with another region — each axis (x/y for move, w/h for resize) is checked independently against the region's *current* value on the other axis, so dragging diagonally toward a neighbor still slides smoothly along whichever axis isn't blocked instead of freezing both at first contact. Regions the dragged one already overlapped *before the gesture started* (`preExistingOverlaps`, computed once per `startDrag` call from the pre-drag rect) are exempt from that check for the rest of the gesture — otherwise a region that starts out overlapping something (a saved config predating this feature, or any other pre-existing imprecision) could never be dragged again at all, not even away from the overlap. `snapToEdges`/`SNAP_THRESHOLD` snap a candidate x/y/w/h to the canvas bounds or any other region's edge when within ~1.5% of the canvas's smaller dimension — without this, free-hand pointer dragging rarely lands on the *exact* value needed for two regions (or a region and the canvas edge) to touch with zero gap, since fast mouse movement can jump straight past that value between two pointermove events; the overlap check then rejects the overshoot and leaves the region a unit or two short of "flush." This only constrains the canvas drag interaction; the number inputs remain fully unconstrained (no snapping, no overlap check) as the precision/keyboard-accessible escape hatch. Client-side validation mirrors `_validate_region` as a UX nicety only — `validate_settings`/`generate_image` are the authoritative server-side checks. `name="regionsJson"` becomes the settings key `generate_image` parses.
- **The "+ Add Region" button is `position:sticky; bottom:0`** (using the `--surface`/`--surface-border` theme tokens, not hardcoded colors, so it doesn't break dark mode) so it stays reachable without scrolling to the bottom of a long region list.
- **Per-region settings editor** (`refreshRegionSettingsEditor` and everything it calls: `fetchPluginPage`, `buildSchemaEditor`, `namespaceFragment`, `stripWidgets`/`stripCheckboxMirrors`, `getFieldValue`/`setFieldValue`, `applyVisibility`, `applyDependentOptions`) — each region gets its target plugin's *real* settings form instead of a raw JSON textarea, without any InkyPi change. Mechanism: `fetch('/plugin/' + plugin_id)` against InkyPi's existing settings-page route (cached per `plugin_id` in `pluginPageCache`, so N regions on the same plugin fetch once), parse the response with `DOMParser`, and pull out `[data-settings-schema]` — the same markup `settings_schema.html`'s macros render for the real per-plugin settings page. If that marker isn't present (a plugin with no `build_settings_schema()`, e.g. `blood_sugar`, whose bespoke `settings.html` isn't wrapped in it), Layout falls back to the original whole-region raw JSON textarea, unchanged, labeled accordingly.
  - **Namespacing**: since N regions can render N copies of the same plugin's form on one page, every `id`/`name` in the cloned fragment gets rewritten with a `region-<uid>-` prefix (`namespaceFragment`) before injection — `<uid>` is a stable per-region identifier (a `WeakMap` keyed by the region object, assigned via `uidFor`), **not** array index, so an in-flight fetch can still find (or safely no-op past) the right DOM container even if regions were reordered/removed while it was in flight. Each element's *original* field name is stamped onto `data-field-name` before any renaming, and all reads/writes into `region.settings` key off that attribute — never off the rewritten `id`/`name` — so the settings dict's keys stay exactly what `generate_image`'s child plugin expects.
  - **Some `[data-hybrid-widget]` types now run for real, per region — `github-colors` and `newspaper-search`** (`LAYOUT_SUPPORTED_WIDGET_TYPES`, `initSupportedWidgets`). This required one small, additive change on the InkyPi side (`src/static/scripts/plugin_schema.js`): `initializeWidgets(root, config, allowedTypes)` gained an optional allowlist filter, and a new public `InkyPiPluginSchema.initWidgetsIn(root, config, allowedTypes)` wraps it — `init()`'s own page-load call is unchanged (`allowedTypes` stays `undefined`, meaning "all"), so every plugin's normal settings page behaves exactly as before. `initSupportedWidgets` calls this with `region.settings` as `config` and the allowlist, **before** `stripUnsupportedWidgets`/`namespaceFragment` run — this ordering matters and is safe: the widget's internal `widget.querySelector("#literalId")`-style lookups need real, un-namespaced ids to find their own elements at init time, but since JS event listeners bind to element *references* (not id strings), `namespaceFragment` running immediately afterward safely renames whatever the widget produced — including its own internal `id`/`for`/`name` pairs — without breaking anything already wired up. Verified end-to-end: two regions both running `github`'s color-picker widget get correctly namespaced ids with zero label/focus cross-talk, independent values, and correct pre-fill when the region's settings come from "Start from existing instance."
  - **The remaining widget types stay stripped**, replaced by an actionable notice rather than an empty box: `findWidgetSections`/`replaceEmptyWidgetSections`/`buildWidgetUnavailableNotice` (called from `buildSchemaEditor` right after `initSupportedWidgets`/`stripUnsupportedWidgets`) capture which `.schema-section`s contained a widget *before* stripping, and for any left with zero `.schema-field` descendants **and no surviving `[data-hybrid-widget]`** (the second condition is what stops this from also firing on `github`/`newspaper`'s now-real, now-supported sections) replace that section's body with a `.settings-callout.warning` naming the section and linking to that plugin's own `/plugin/<id>` settings page, pointing at "Start from existing instance" as the way to set it. Confirmed still correctly firing for `calendar`, `image_upload`, `clock`, `weather`, `todo_list` (`calendar`/`image_upload` hard-crash `generate_image()` via `RuntimeError` if never set any other way; the rest silently stick on a default) — `ai_image` remains unaffected either way, since its widget owns zero settings keys and its section has other real fields alongside it.
  - **Phase 2 — `clock-face-picker` and `weather-map` are now also supported**, and along the way surfaced two real, independent bugs, both fixed:
    - **Neither widget originally notified anything when its *primary* interaction completed.** `initClockFacePicker`'s `selectOption` set `hidden.value` (the actual `selectedClockFace`) via plain property assignment with no dispatched event — only the two *secondary* color fields it also touches were ever announced (via `setColor`'s explicit `dispatchEvent`). `initWeatherMap`'s `closeModal` had the identical gap for `latitude`/`longitude` — the two fields this entire widget exists to set. Both now dispatch a `change` event after setting the value, matching the pattern `setColor` already used — a real bug on the *real* plugin pages too (anything relying on `input`/`change` there was equally blind to these), not something Layout's integration introduced, just the first thing to actually depend on hearing about it.
    - **A `<script>` element parsed by `DOMParser` (as every widget fragment is, via `fetchPluginPage`) has its "already started" flag permanently set by the HTML spec — it will never execute, not even fetch, no matter how it's later cloned or inserted.** Confirmed directly: a cloned `<script src="leaflet.js">` sat in the live DOM for 4+ seconds with zero network request, while a `<link rel=stylesheet>` cloned the same way fetched and applied completely normally (no such restriction exists for stylesheets — only scripts). `loadWidgetScripts` strips every widget-embedded `<script src>` from the fragment and, for each unique URL, creates a *fresh* `document.createElement('script')` instead — the only way to actually load it — deduped across regions via `loadedWidgetScriptUrls`/a live-DOM check so N weather regions still only fetch Leaflet once. `dedupeWidgetAssets` (unaffected by the above) handles the `<link>` case, which just needs de-duplication, not a different loading mechanism. On the InkyPi side, `initLeafletMap` also gained a small bounded retry (up to 20× 150ms) for the case where the map modal opens before that freshly-created script has finished loading — a real robustness gap for any dynamic consumer, harmless for the normal page where Leaflet is already loaded long before the button is even clickable.
    - Verified end-to-end: two `clock` regions with independently selected faces and correctly captured `selectedClockFace`/colors; two `weather` regions with exactly one Leaflet `<script>`/`<link>` in the live DOM despite both loading the widget, and a real map-click round-trip correctly capturing non-default `latitude`/`longitude` into `region.settings`.
  - **Remaining widgets stay out of the allowlist, phased and scoped, not a trivial flip**: `calendar-repeater`/`todo-repeater` need a small InkyPi-side seeding-guard fix (`initCalendarRepeater`'s `if (!list.children.length)` seed-from-config check never fires, since `calendar_repeater.html` always server-renders exactly one blank row) *and* Layout-side work for rows added later via the widget's own "Add" button, which get plain un-prefixed `name="calendarURLs[]"` after Layout's one-time namespacing pass already ran — not a collision risk for value-reading (Layout never relies on document-wide `name` uniqueness, only fragment-scoped queries), but `getFieldValue`/`setFieldValue` currently have zero array-field support and would need it. `image-upload-list` is likely permanently out of reach regardless of scoping (`globalThis.__INKYPI_UPLOADED_FILES__` is keyed by a literal string shared across all regions, and a native `FileList` has no representation in `regionsJson`'s single JSON string — an architectural gap in Layout itself). `ai-image-prompt-tools` does two unscoped `document.querySelector` calls with no root parameter at all and would need an InkyPi-side rewrite before it could ever join the allowlist — low priority, since this widget owns zero settings keys and Layout is unaffected by leaving it stripped indefinitely.
  - `applyVisibility`/`applyDependentOptions` are JS re-implementations of `settings_schema.html`'s `is_visible` macro and `options_by_value` dependent-select logic, reading the same `data-visible-if-*`/`data-options-source-field`/`data-options-map` attributes those macros already emit — deliberately duplicated (not shared code) since the canonical versions live in InkyPi's `plugin_schema.js`, which this plugin has no way to load safely for multiple simultaneous instances (see above).
  - **Real runtime dependency, new**: this only works because InkyPi's `/plugin/<id>` page happens to emit `[data-settings-schema]`/`data-visible-if-*`/`data-options-*`/`[data-hybrid-widget]` in a stable, scrapable shape. If that markup is ever restructured, this degrades silently (fields stop appearing, or a schema-driven plugin falls through to the raw-JSON path) — no test in this repo would catch it, only the manual browser pass described in "Verifying changes." Everything else in this plugin is self-contained; this is the one place it reaches into InkyPi's actual page output rather than just its plugin-loading conventions.
- **Clone settings from an existing instance** (`refreshCloneOptions`, `listExistingInstances`, `fetchInstanceSettings`, `extractPluginSettingsFromDoc`/`extractJsonAfterMarker`, `stripStyleSettings`) — a "Start from existing instance" `<select>` per region, populated by fetching InkyPi's existing `/playlist` page (cached once per page-load in `playlistPagePromise`, since it lists every instance of every plugin across every playlist) and filtering its `.plugin-item[data-plugin-id][data-instance-name]` rows to the region's target plugin. Picking one fetches that instance's own settings page (`/plugin/<id>?instance=<name>`, the same route `refreshRegionSettingsEditor` already fetches) and reads its settings directly out of the `window.pluginSettings = {...}` object every such page embeds (`extractJsonAfterMarker` does a brace-matching scan, not a regex, since a settings *value* could itself contain `};`) — this works uniformly for schema and non-schema plugins alike, unlike scraping rendered field values, and is the only way to recover a non-schema plugin's (`blood_sugar`) settings at all. **This is a one-time copy into `region.settings`, not a live link** — the region stays independently editable afterward, and the source instance is never touched. `stripStyleSettings` drops the generic frame/margin/background/text-color keys every plugin's *full* settings page also embeds in that same JSON (they live in `plugin.html`'s own Style tab, entirely outside any `[data-settings-schema]` content, so a region's rendered form has no field for them and would otherwise silently stuff them into the "Advanced settings" JSON box) — `HOME_PRESET`'s own region settings never include them, and they're meant for a full-screen rendering, not a cropped region.
- **Save-time bounds checking, and why there isn't any**: `BasePlugin.validate_settings(self, settings)` has no `device_config` parameter by interface (true for every plugin, not Layout-specific), so it cannot know the canvas size. It used to bounds-check against a hardcoded 800×480 anyway, which **rejected every valid region on any larger panel** — a full-screen region on a 1600×1200 device failed to save at all, making the plugin unusable there. That check is gone; `validate_settings` now runs only `_validate_region_shape`. Bounds are enforced in `generate_image` against the real resolution, and the settings page's own canvas validates live against the same real resolution, so the user still gets immediate feedback while editing. Don't reintroduce a hardcoded canvas here — pin the behavior via `test_validate_settings_does_not_assume_an_800x480_canvas`.
- **`_list_available_plugins`** — scans InkyPi's `plugins/` directory for any folder with a `plugin-info.json`, excluding `base_plugin` and Layout itself (a region can't target `layout` — enforced both here for the UI dropdown and as a hard `RuntimeError` in `_parse_regions`).

### Things worth knowing before changing behavior

- Region bounds are enforced in exactly one place: `generate_image`, against `device_config`'s real resolution via `get_oriented_dimensions`. `validate_settings` deliberately checks only resolution-independent shape (see above) — adding a canvas size there means guessing, and a wrong guess blocks valid saves.
- The cache key includes a hash of the region's `settings`, so editing a region's settings (not just moving/resizing it) correctly invalidates its cache rather than reusing a stale render for different settings.
- `_call_child_plugin` always converts the child's returned image to `"RGB"` before compositing — child plugins are otherwise treated as complete black boxes; Layout never inspects or modifies their internal rendering logic.
